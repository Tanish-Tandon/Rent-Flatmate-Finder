# System Design – Rent & Flatmate Finder

## 1. Compatibility Scoring Architecture

The platform uses an AI-powered compatibility engine to rank room listings for tenants."To optimize LLM API usage and reduce costs, the system computes compatibility scores dynamically when a tenant expresses interest in a specific listing, rather than on every search or profile update."

The score generation process considers two primary factors:

* Preferred location match
* Budget compatibility

Instead of recalculating scores on every search request, the generated score and explanation are stored inside a dedicated `CompatibilityScore` collection. This reduces API latency and minimizes LLM API usage.

When tenants browse listings, the backend simply fetches precomputed scores and returns listings sorted in descending order.

---

## 2. LLM Integration and Fallback Mechanism

Compatibility scoring is generated using an LLM such as OpenAI or Gemini.

The backend sends both the room listing details and tenant preferences to the model and expects the following JSON response:

```json
{
  "score": 92,
  "explanation": "Excellent match because the room falls within the tenant's budget and preferred location."
}
```

Since external AI services may experience downtime or rate limits, the platform implements a rule-based fallback mechanism.

Fallback rules:

* Exact location match → 60 points
* Budget within range → 40 points
* Partial location match → 20 points

This guarantees that compatibility ranking remains available even if the LLM service becomes unavailable.

The system records whether the score was generated by the LLM or by the fallback engine for monitoring purposes.

---

## 3. Interest Request Workflow

A tenant can express interest in a listing by creating an interest request.

The request enters a `pending` state and becomes visible to the owner.

The owner can:

* Accept the request
* Decline the request

Upon acceptance, the system creates a conversation between the tenant and owner and enables real-time messaging.

Filled listings are automatically hidden from future searches.

---

## 4. Real-Time Chat Implementation

The application uses Socket.IO for real-time communication.

Each accepted request generates a dedicated conversation room identified by a conversation ID.

When a message is sent:

1. The message is stored in MongoDB.
2. The backend emits the message to connected participants.
3. Both users receive the message instantly.

Persisting messages ensures that users can continue previous conversations after refreshing the page or reconnecting.

The chat system follows an event-driven architecture and keeps the implementation lightweight while supporting multiple simultaneous conversations.

---

## 5. Notification Flow

The platform sends email notifications for important events.

### High Compatibility Interest

If a tenant with a compatibility score above 80 sends an interest request, the owner receives an email containing:

* Tenant details
* Listing information
* Compatibility score

### Owner Response

When the owner accepts or declines the request, the tenant immediately receives an email notification.

The notification process is asynchronous and does not block API responses.

---

## 6. Scalability Considerations

To improve scalability:

* Compatibility scores are precomputed and cached in the database.
* WebSocket connections are separated from REST APIs.
* Chat messages are stored independently from listings.
* Email notifications run asynchronously.
* Database indexes can be added on location, rent, and compatibility score.

This design keeps the platform responsive while supporting increasing numbers of users, listings, and conversations.
